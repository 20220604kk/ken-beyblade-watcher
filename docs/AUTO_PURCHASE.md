# 自動下單功能：FUNBOX／誠品

本文件分開說明派單、購物車與結帳。監控方式見 [平台監控](MONITORING.md)。以下描述目前程式能力，不是成功率承諾，也不附作者的帳密、地址、門市、訂單或結帳範本。

## 1. 派單總管

```text
可購候選 → 黑名單排除 → 白名單資格 → 心願關鍵字優先
         → 各帳號已購／保留額度、配送、登入核對 → 帳號佇列
         → 單品一單 或 多款合單 → 平台執行器
```

核心程式：[purchase-rules.js](../src/purchase-rules.js)、[purchase-dispatcher.js](../src/purchase-dispatcher.js)、[purchase-ledger.js](../src/purchase-ledger.js)、[auto-purchase.js](../src/auto-purchase.js)。

- 黑名單優先：即使同時命中白名單／心願，也不派單；仍可有監控情報通知。
- FUNBOX 必須命中白名單。誠品發佈範例設定為 `whitelist`；程式另保留其他購買模式，不能把範例預設當成所有舊設定都已強制改過。
- 優先關鍵字左邊較優先，同一優先群依發現順序；未命中優先級的合格商品依帳號任務的隨機 rank 排序。
- 優先級不跳過限購、庫存、配送與含運金額限制。額度保留也納入判斷，避免同帳號重複派送。
- 每帳號有獨立佇列及單品／合單設定；同帳號序列化，不同帳號有限並行。多帳號不應用來規避官方限購。
- 單品模式：一款商品形成一張單，再處理下一個任務。
- 合單模式：在短收集窗內選取同帳號、同平台的可執行任務，依序加入同車；受最大品項、建車時間及總額限制。允許部分成交時可剔除明確售罄款，保留其他款送一張單。

「合單」不是並發向同一車重複送單，也不會等待所有商品都成功才無限期卡住。

## 2. 帳號購買規則

| 平台 | 本機派單政策 | 證據／限制 |
| --- | --- | --- |
| FUNBOX 一般款 | 每帳號同款每日 1 件 | 使用者設定的保守假設，不當作已驗證的全站官方規則 |
| FUNBOX 隨機強化組 | 每帳號同款每日合計最多 3 件；數單合計扣額度 | 使用者提供的觀察；仍受即時 stock、qtyCap 與官方拒單限制 |
| FUNBOX 跨日 | 以台北時間午夜切換每日帳本 | 人工採用的重置假設，官方實際重置時間未驗證；未知訂單不因跨日自動釋放 |
| 誠品 | 帳號已有同款購買紀錄時不再派單 | 使用者確認後採用的已購排除政策；本機須有紀錄／同步，官網限購判斷仍優先 |
| 超商配送 | 命中設定的超商禁送關鍵字時，不走 7-11 取貨付款 | 商品材積與官方當次配送選項仍須核對 |

本機帳本不是網站全部購買歷史。手動下單、其他裝置下單或尚未同步的訂單，仍可能造成官方限購拒絕。

## 3. 共通交易步驟

登入、帳號資格與未知訂單保護會先核對。2026-10-19 交接版正常購買不固定先清車，改由使用者在控制台一鍵全清；未知送單結果尚未解除時仍禁止清車。不得依舊流程描述把固定清車重新放回購買熱路徑。

| 階段 | 要確認的事情 |
| --- | --- |
| 手動全清 | 僅在明確操作且無進行中／未知交易時，逐帳號核對並清空；不是每筆購買前固定步驟 |
| 核對派單 | 帳號身分、佇列／任務、商品及規劃數量一致 |
| 加車 | 單品或依序合車；加車回覆不明先讀車，不盲目再加 |
| 核對購物車 | 商品與數量符合本次任務，不混用其他帳號或上一單 |
| 準備結帳 | 讀取本次購物車的配送、付款與收件資料；強制紅利 0 |
| 核對方案 | 即時付款可用、門市有效、配送相容、含運總額未超限；備援切換後重新核對 |
| 送單 | 同帳號單一路徑；有上限、有總時間期限，不並發重複提交 |
| 核對結果 | 官方訂單號／明細、商品數量、金額及付款方式一致；ATM 再讀轉帳資訊 |
| 記帳與下一筆 | 保存帳本、訂單狀態與日誌；明確結束才往下，結果不明則保護該帳號 |

日誌以編號步驟、時間、累計秒數、動作、狀態／下一步呈現，可匯出 TXT。官方 HTTP 200 或顯示「資料已備妥」，都不能單獨認定訂單成立。

## 4. FUNBOX 自動下單

主要程式：[funbox-cart.js](../src/funbox-cart.js)、[funbox-api-checkout.js](../src/funbox-api-checkout.js)，帳號與工作協調在 [auto-purchase.js](../src/auto-purchase.js)。

使用帳號登入 session 呼叫網站自身端點：核對派單、加車、取得本次結帳契約、設定紅利為 0、讀取配送付款、送出訂單，再讀官方訂單明細。固定清車已移出正常購買路徑。部分契約／結果以 HTTP 取得 HTML 並解析，因此「走 API／HTTP」不代表所有資料都是 JSON；主交易路徑不依賴逐步點擊結帳頁。

### 付款

- ATM：使用宅配收件資料，成立後核對單號、銀行代碼／帳號、金額及期限；不自動匯款。
- 7-11 取貨付款：使用有效門市資料與當次可用方案；首次選店需經官方門市流程，不只把顯示名稱填進送單內容。
- 網站選店回傳後再次核對紅利 0，避免網站自動重新套用。
- 指定方式不可用且尚未送單時，程式有一般宅配 LINE Pay 備援路徑；仍須官方提供相容選項並符合資料／總額限制，不保證每個帳號、商品都可切換。
- LINE Pay 訂單成立只代表待付款，不代表已付款；保留時間以官方回應為準。

### 庫存衝突

409 先補查即時 variant／庫存／數量限制；明確售罄不繼續撞同一請求，必要時依確認結果降量。未變的售罄庫存簽名抑制重複任務，新的庫存觀測才重新評估。逾時或 5xx 不能直接當成「沒加到」而重加。

## 5. 誠品自動下單

主要程式：[auto-purchase.js](../src/auto-purchase.js)、[eslite-batch-cart.js](../src/eslite-batch-cart.js)、[eslite-account-setup.js](../src/eslite-account-setup.js)、[eslite-orders.js](../src/eslite-orders.js)。

現行主入口購買採 API-only：本帳號 session、核對派單、加車、會員／配送付款資料、報價、`orders/checkout`、查單；不再每筆固定清車。缺必要結帳資料或登入失效時，不以瀏覽器點擊結帳作為不透明替代。

### 付款與備援

- 宅配 ATM：可共用收件人／地址等普通配送資料，但每帳號使用自己的會員身分、session 與當次交易資料；不能複用別帳號 token 或舊訂單轉帳帳號。
- 7-11 取貨付款：需要該帳號可用的官方門市／結帳資料，並通過商品配送核對。
- 使用者要求超商付款但缺可用資料時，先檢查共用宅配 ATM 是否就緒；就緒才切換本次任務，不修改使用者原來的付款偏好。
- 所有路徑的送單 `discount_point` 固定為 0；不能因舊範本有紅利就自動套用。
- 指定方式即時失效時，先核對相容 ATM 備援及含運金額。宅配 LINE Pay 仍需官方一次性付款憑證 provider；目前正式串接與實單驗收未完成，不能宣稱一定能救單。
- 登入、人工驗證及首次資料建立仍可能需官方網頁；這與 API-only 的交易執行路徑是不同階段。

## 6. 失敗、重試與下一筆

| 情況 | 處理 |
| --- | --- |
| 加車逾時／回覆不明 | 先讀車確認；無法確認就保護本帳號，不重複加到超量 |
| 明確售罄／限購 | 排除該款；合單允許部分成交時保留其他款，不反覆撞同一錯誤 |
| 明確忙碌拒單、判定尚未接受 | 在期限內有限重試；主要送單路徑最高 3 次，不等於所有錯誤都重試 3 次 |
| 送單逾時／結果不明 | 先查單；不重送、不清車、不拆單，以免重複訂單 |
| 登入失效／人工驗證／帳號排隊 | 停該帳號交易並呈現待處理狀態，不繞過驗證，不讓該帳號佔住其他帳號的工作 |
| 超過本次含運金額上限 | 不送單；不能為追求成功而自行加價或超出授權 |
| 已確認成立／已確認失敗 | 記帳或釋放對應額度，再處理後續合格任務；不可重試狀態與候選變更由佇列重新判斷 |

重試同時受平台執行器與任務期限限制。FUNBOX 連續派單的外層重試和內層送單重試是不同層級，不能相乘成無限制請求。LINE Pay 的一次性憑證尤其不能盲目重複使用。

查單未能確認時，本帳號的 hold 與保留額度不自動解除；其他帳號可獨立繼續。確保不重複下單，比把結果不明當失敗硬往下跑更重要。

## 7. 成果與支援邊界

- 訂單成立、待付款、付款成功、取消是不同狀態；控制台可查官方狀態，不把本機最初成功紀錄永久當成最新狀態。
- ATM 資訊與訂單通知走私人目的地，公開商品通知不包含收件資料／轉帳帳號。
- 只有取得並核對官方訂單證據才記錄成立；測試、預熱、付款選項探測不能當成實單。
- 不保證特定秒數、成功率或補貨能買幾單；登入、官方限流、庫存競爭與端點變更仍會影響成果。
- 本文件聚焦 FUNBOX／誠品；其他來源的監控、日亞獨立商品頁任務，不能視為已共用或驗證同一 API 流程。
