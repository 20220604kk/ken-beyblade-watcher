# 日亞 A：三步直購

日期：2026-10-16，Asia/Taipei。

## 使用者看到的購買紀錄

```text
01｜商品頁面｜發現直接購買｜成功
02｜安全結帳｜發現購買按鈕｜成功
03｜取得訂單｜取得訂單編號 <正式單號>｜成功
```

這是成功時的格式，不是本次建立了新訂單。失敗停在對應步驟；送出後缺正式單號只能寫「待核對」。步驟之外不再塞逐個 HTTP 請求、毫秒計時或英文事件名稱。舊加車紀錄不改寫成直購成功。

## 真正的執行變更

- 僅 A 且 API／fastLane 開啟時走新路線。B、C、獨立日亞監控與其他平台不切換購買策略。
- AOD 原價／自營偵測仍維持原定 2 秒目標間隔，不重疊，不繞限流。
- 命中後讀取正式商品頁的當次立即購買表單 → POST 官方 `/gp/product/handle-buy-box/…` → 讀取其結帳回覆 → POST 該回覆提供的正式送單表單。
- 不讀購物車、不加車、不再查車、不走 `/checkout/entry/cart`，也不在命中後查舊訂單。商品頁沒有合格的直購表單時停止，不偷偷切回加車。
- 送出前在已有的結帳回覆內核對唯一 ASIN、1 件、自營、JPY、原價上限、運費、配送及不折點數。這些是本地解析與核對，不額外開頁查詢。
- 商品頁即使顯示 TWD，也不自行換算。僅在商品頁自營報價識別與剛取得的 AOD 報價精確相符時沿用其 JPY 報價，最終仍核對並提交官方 JPY 選項；報價不符或缺少綁定就停下。
- 官方必要跳轉仍需 HTTP 請求；三個業務步驟不等於承諾只有三個網路請求。

## 待機作業與單號

- 第一次排程檢查前準備官方訂單識別基準；缺貨待機時超過 20 秒才更新。收到即時補貨訊號時跳過這項準備，不等它才購買。
- 只在基準為同 ASIN、於直購開始時不超過 30 秒才使用；沒有／過期時不臨時補查來拖慢直購。
- 完成頁若有唯一正式訂單明細連結或明示單號，直接取得；沒有時，僅在送出後利用事先準備的基準查官方新訂單，再核對完整明細。多張吻合／資料不明不猜單號。
- `purchaseId`、`executionId` 不是正式單號，禁止拿來填第 03 步。失去完成回覆且無可用基準時保留待核對，不重送。
- 第 500、1000…次未符合購買條件的檢查後才清理活動購物車；合格商品優先，不為了湊清車次數先整理。清車使用當次官方刪除表單，只刪活動車，不碰稍後購買。每輪最多 25 件。
- 同帳號購買、待核對交易、登入、驗證、冷卻時不清車。清車回覆逾時只查一次確認，不盲目重播刪除。
- 清車狀態另顯示在待機資訊，不插入三步購買紀錄。

## 本次實站驗證界線

使用 computer-use 檢查使用者附件的 BX-11（B0C533Q31X）。一般 Chrome 的「現在購買」確實進入安全結帳頁，可見正式 `spc-form` 與送單按鈕；沒有按最終送出、沒有建立新訂單。官網同時將 BX-11 放入活動車，取得使用者當次同意後，只刪除這件測試品，畫面確認成功刪除；稍後購買未動。

唯讀查看使用者自己完成的訂單頁，確認該頁只有成功提示與前往訂單列表的連結，沒有可直接讀取的正式單號；因此第 03 步保留必要的送出後官方查單。

亦核對該筆既有訂單的官方明細：單件商品沒有「數量：1」標籤。查單不以缺欄位就當 1 件，而是要求同 ASIN、正式單號、自營、JPY 含運與運費均吻合，且官方商品小計及自營單價同時等於已核對的一件價格，才可由金額證據確認一件；缺其中任一項仍待核對。TWD 訂單不冒充 JPY 訂單。

安全結帳實頁的配送地址位於 `#change-delivery-link #deliver-to-address-text`，不在舊的 `#shipping-address`。已加入此實際選擇器及回歸測試；只有「正在发送至」標題、沒有地址內容仍不放行。

以上是真實前端頁型與欄位證據，不是新 API 直購已成交的證據。新 API 路徑、取消、錯商品／賣家／價格／數量／配送／紅利、逾時、基準過期、500 次清車與三行紀錄皆有合成資料測試。最終全部套件重跑 928 項通過。

依完整流程驗證技能另核對正式 `/api/status`、前端三行輸出與頁面錯誤，不以單元測試代替實站成交。A 原本 `adding` 待核對交易保留，未擅自解除或重新購買。正式單號端到端耗時仍未實測，不宣稱已省下多少秒。
