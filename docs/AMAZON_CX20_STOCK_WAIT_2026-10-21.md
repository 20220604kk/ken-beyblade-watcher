# 10/21 日亞 CX-20：紅字續查、重試與登入修復

接續 [1020 修改文件](HANDOFF_2026-10-20.md)。只使用既有網頁 HTTP，未導入 Amazon 官方商品 API。

修正前 A／CX-20 當日 11 次紀錄均未執行最終送單，成功 0 筆：2 次缺貨誤分類為表單缺失，2 次在登入跳轉提前判失效，7 次為結帳數量降為 0。這些紀錄無 429／503。普通失敗原採 2／5／30 秒，三次 30 秒共空等 90 秒。

| 狀態 | 最終行為 |
|---|---|
| 商品正常等待／普通失敗 | API fastLane 改為 1 秒目標週期；普通重試移除 5／30 秒累進等待。非 fastLane 維持原週期 |
| 紅字請求數量無法提供、數量 0 | 保留本次官方結帳位址，只 GET 重查；不重加車、不重播 Buy Now、不按數量 0 的下一步 |
| 紅字回流 | 解析當次表單，重新核對目標、數量 1、自營、配送、運費、含運總額、點數，再取得原有送單授權 |
| Amazonカートは空です | 清除續查位置，回商品頁等待新報價 |
| GET 逾時、暫時空頁、價格或資料不符 | 保留原位置，下輪仍 GET；不因此重加商品 |
| 單純官方 GET 登入跳轉 | 跟隨 GET；實際登入表單才判定需登入，MFA／CVF 分類為驗證 |
| 結帳真實登入表單／驗證 | 獨立標示；商品監控繼續，結帳等待官方登入／驗證後再核對 |
| 真實 429／503／Retry-After | 遵守冷卻，不以高頻繞過 |
| 最終 POST 後未知 | 保留交易鎖，只核對訂單，不重送 |

紅字頁以請求開始到下一次開始 1 秒為目標。回應超過 1 秒時不再額外空等，但同帳號仍只有一個請求執行；無法保證網路每秒完成。商品讀取也不併發追趕。

紅字競爭可能持續很久，回流後不沿用進入前的舊訂單基準推認新單；完成頁缺正式單號就保留未知，避免把期間其他手動訂單算成本流程成功。

## 接手位置

- `src/amazon-checkout-stock-wait.js`：日／中／英空車與缺貨、ASIN 核對、可重查路徑白名單。
- `src/amazon-jp-http.js`：循序 GET、續查、官方登入跳轉、送單驗證與證據。
- `src/amazon-jp-product-order.js`：私人持久化續查、1 秒排程、結帳登入獨立狀態；保留位置時禁止待機清車及背景基準準備。
- `src/amazon-pre-submit-retry.js`：普通 1 秒，官方冷卻優先；未知最終送單及已用競速授權不可解鎖。
- `src/dashboard.js`／`src/amazon-three-steps.js`：紅字等回流、空車返回、範圍明確的登入提示。

`checkoutStockWait` 包含工作階段 URL，只放本機私人 state；狀態 API 僅公開 active／since／refreshCount。不得將 state、Cookie、原始結帳 URL 推 Git。記憶體請求軌跡最多 60 筆，重查計數不每秒寫磁碟。

重啟依已證明的 buy_now／未最終送單階段恢復 GET。舊版只依登入跳轉建立的 checkout needs_login 可重新核對；舊輔助登入快取只失效一次。新版真實表單建立的結帳登入狀態不靠重啟解除。完成官方互動登入只允許重新嘗試，不代表結帳已驗證。

## 驗證與限制

離線覆蓋截圖關鍵字、多輪回流、空車、逾時續查、未知頁保留、429／503、停止、商品／數量／賣家／混車／點數錯誤、登入跳轉、驗證、未知最終送單、狀態去秘密。入口為 `npm ci`、`npm run check`、`npm run handoff:phase1`；實際收據綁 commit，驗收輸出放本機 `artifacts/handoff/amazon-stock-*`。

實站紅字曾由 POST `/checkout/entry/buynow` 回傳。本次只用實際回傳位址 GET，不杜撰 flow ID、不重送 POST。同一工作階段能否持續取得回流頁需以後續實站回應確認；合成測試不代表已搶到庫存或訂單，不得為驗收自行新增真實購買。

部署須等交易／互動登入空檔，保存當下設定後暫停、重載、恢復，核對設定與帳本，保留目標及成功計數。回滾只回滾程式，不覆蓋私人歷史。
