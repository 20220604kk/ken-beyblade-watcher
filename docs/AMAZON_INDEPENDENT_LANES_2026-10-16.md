# 日亞監控與自動下單：兩條獨立線

日期：2026-10-16（Asia/Taipei）。本次不改帳號、購買上限、付款方式或輪詢速度，不建立真實訂單。

## 執行方式

```text
日亞監控線：搜尋／商品直查 → 每款核對完成即交付補貨訊號 → 繼續查其他商品
                                      ↓ 單向提示，不等待下單結果
日亞下單線：自己的目標輪詢／接收提示 → 帳號內核對 → 結帳 → 查單確認
```

- 原本已有各自的計時器、執行鎖及瀏覽器 profile，不需要重建第二套服務。
- 本次移除「等整批核對完成才交付訊號」的相依關係。一般搜尋、已知單品直查及定價前專線都在取得每款結果時交付。
- 訊號回呼不等待結帳；同步拋錯或非同步拒絕不會中止監控。Discord 仍依序傳送，但不再擋住後續商品的購買訊號。
- 每輪同 ASIN 只交付一次。同一輪後續網頁失敗時，保留已完成觀察並嘗試傳送其通知；下輪不把已交付的同一次可購轉換重播。
- 通知失敗會留在獨立的待送清單，下輪重試通知，不重播購買訊號。
- `hybrid` 下單任務會自行輪詢，不依賴一般監控成功。使用者明確選擇的 `scan_signal` 模式仍只接收訊號，沒有偷偷改成輪詢。
- 保留同一任務的交易鎖、冷卻、登入／驗證暫停及未明送單先查單規則。此改動不是新增跨 A／B／C 的帳號識別或交易鎖。

## 獨立的範圍

這是同一 Node.js 服務內的非同步流程獨立，不是兩個作業系統程序。CPU、網路、狀態檔的序列化寫入仍共用，不能宣稱資源完全隔離。

本次也沒有拆開「一般監控內部」的搜尋、型錄與普通直查；搜尋失敗仍可能讓當輪尚未開始的普通直查不執行，但不會阻止獨立的 hybrid 下單輪詢。

未變更 AOD 解析、非空購物車接續結帳或立即購買契約。不能把此次拆線測試當成這些問題已修好，或當成補貨一定能成交的證明。

## 離線驗證

`test/amazon-independent-lanes.test.js`：

1. 第一款核對成功時，後面商品尚未查完就已交付訊號；消費端未完成不影響監控。
2. Discord 第一則尚未送完，三款購買訊號已全部交付。
3. 訊號消費端同步／非同步失敗，監控仍完成。
4. 首次基線、覆蓋升級及未變動可購狀態保持安靜。
5. 定價前專線在一般搜尋開始前交付訊號。
6. 後續商品讀取受限不撤銷先前訊號，也不重播已完成的可購轉換。
7. 一般監控查詢卡住，下單線仍可用自身輪詢完成模擬交易。
8. 下單結帳卡住，監控仍完成；重複訊號不能多開一筆交易。
9. Discord 傳送失敗後可重試通知，但不重播購買訊號。

以上只使用記憶體假頁面／假 API／假單號，不接觸 Amazon、不加車、不付款。

`scripts/amazon-priority-replay.mjs` 已改為驗證新相依關係：每款核對在虛擬 1／2／3 秒完成，訊號也在虛擬 1／2／3 秒交付。這不是實站速度測量，也不代表每張訂單實際節省兩秒。舊的 10/15 研究報告仍保留為歷史結果。
