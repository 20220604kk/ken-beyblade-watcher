# FUNBOX／誠品：多角度測試測驗

目標：驗證近幾天累積的監控、登入、派單、單品／合單、付款、異常補救、帳本、表格及日誌。不是只追求「跑過幾個測試」，而是回答：買對商品、用對帳號、沒有重複送單、碰到問題仍可恢復，使用者看得懂結果。

## 1. 如何執行

在專案根目錄雙擊 **購物網站多角度驗收.cmd**，或執行：

```powershell
npm run test:commerce
```

預設完全離線，不登入官網、不清正式購物車、不推播、不建立真實訂單，不重載正式服務。測試使用假 API、假身分及臨時檔案，報告放在 `artifacts/commerce-acceptance/<執行時間>/`。

需要額外查看當前本機標籤時：

```powershell
npm run test:commerce -- --runtime
```

這只 GET 本機 3210 的狀態，不替任何帳號驗證官網，也不操作登入器。子測試禁止存取正式 3210、官網、常見正式資料路徑及啟動真實瀏覽器；只允許測試的臨時本機伺服器。防護是 Node 測試程序的攔截器，**不是作業系統沙箱**，不可拿來執行不受信任程式。

輸出：

- `REPORT.md`：六面向結果、18 種模型比較、失敗位置與尚未驗收項目。
- `report.json`：逐項測試、檔案行號、來源 SHA-256、執行環境、本機唯讀狀態。
- 六個分組 JSON：方便交給 AI 精準定位回歸，不匯出原始 assertion、請求頭或帳密。
- `shared-stock-replays.json`：ABC 每個任務的順序、時間、品項、假单號、略過原因。
- `SUMMARY.txt`：最短結論；`latest.json` 指向最新一輪，不刪除舊報告。

## 2. 四道關卡，不能互相冒充

| 關卡 | 要證明什麼 | 如何驗證 | 本套件預設 |
| --- | --- | --- | --- |
| A 離線回歸 | 程式遵守規則、錯誤处理與持久保護 | 正式模組＋假 API／臨時儲存／故障注入 | 自動執行 |
| B 實際控制台 | 顯示、設定傳遞、下載及操作都正確 | 隔離控制台的真實瀏覽器＋console＋TXT | 另行操作，未跑不能說通過 |
| C 官網唯讀 | 現在的帳號身分、選項與明細契約可用 | 官方 GET；不按可能清車的「檢查」代替 | 另行核對 |
| D 真實建單／補貨 | 實際取得正確訂單、付款資訊與門市 | 明確預算授權後實單；再觀察真實補貨 | 未授權，不執行 |

六面向全綠只會得到 `OFFLINE_PASS_LIVE_NOT_VERIFIED`。任何分組失敗、略過、逾時或没有案例回報，都不能得到離線通過；測試途中來源檔改變會標 `SOURCE_CHANGED_RERUN`，必須重跑，避免驗錯版本。未完成 B/C/D 不給「整套搶購已最佳」結論。

## 3. 六面向必考題

下表是需求對照表；一個題目可由數個既有測試共同驗證，不把題目數當作獨立測試數。測試歸屬與逐項結果以本輪 JSON 為準。

### 01 監控與訊號交接

| 題號 | 注入情況 | 合格答案 |
| --- | --- | --- |
| M01 | FUNBOX 分類／集合回傳同商品、數字 ID 不同 | 依商品路徑合併，只派一份新訊號 |
| M02 | 快來源先回、另一來源一直慢 | 快來源即時交接，不等整輪完成 |
| M03 | 整輪 API 逾時／未知 | 不當成全站售罄，不把未知更新成新鮮可購 |
| M04 | 誠品策展出現多款，搜尋端 429 | 可用策展仍交接；搜尋限流不當成登出 |
| M05 | 只有 stock 正數、但官方禁止加車／尚未開賣 | 不當成明確可購 |
| M06 | 快取、歷史基線、未來時間、監控已停止 | 不製造新購買工作 |
| M07 | Discord 遲到或限流 | 購買不等待推播；通知去重獨立處理 |

證據：monitor 分組、`eslite-overhaul`、`eslite-continuous-tasks`。來源程式的 fake-fetch 測試不代表本輪官方端點健康。

### 02 名單、派單、佇列與額度

| 題號 | 注入情況 | 合格答案 |
| --- | --- | --- |
| Q01 | 同款同時命中黑白名單與優先字 | 黑名單最高，不能加車；監控通知不受購買黑名單影響 |
| Q02 | FUNBOX 未命中白名單；誠品切 all／whitelist | 各自依設定，不因共用總管擴大購買範圍 |
| Q03 | BX-09 與 BX-090、三款都命中強化組 | 型號不誤中；同優先組按發現順序，其餘各帳號隨機 |
| Q04 | A 已買 UX-03，B/C 未買 | 誠品只排除 A，重啟／跨日仍排除 |
| Q05 | FUNBOX 強化組同日已買 2 | 下一工作只准買剩餘 1；不能再加 3 |
| Q06 | 一般款當日已買／跨台灣午夜 | 當日排除、隔日額度可用；此規則與午夜重置標示人工假設 |
| Q07 | 換標籤或換帳號、A→D、AA 以上帳號 | 以帳號身分隔離，不繼承另一人登入、門市、已購或工作 |
| Q08 | A 合單、B 單品；排隊中修改名單／新優先商品到來 | 各自排序；新款不混入已開始的結帳；排除待處理不合資格工作 |
| Q09 | 一帳號卡住、另兩帳號正常 | 同帳號改車串行；其他帳號繼續；保留併行上限 |
| Q10 | 有不明已送單，跨午夜、重啟或人工解除 | 保留額度／整車；人工确认未成立才解鎖，且仍需新鮮觀測 |

證據：dispatch、identity、recovery 分組。每日額度不是繞過官方限制；取消訂單不推測額度已返還。

### 03 登入、身分與結帳資料

| 題號 | 注入情況 | 合格答案 |
| --- | --- | --- |
| I01 | 頁面看似已登入，但 token 到期／會員 API 401 | 不顯示 API 就緒；按恢復規則處理 |
| I02 | API 403、逾時、系統忙碌 | 不直接宣告登出，不清憑證，不反覆開登入器 |
| I03 | 真正可見人工驗證／隱藏驗證欄位 | 真正驗證交人；隱藏欄位不誤擋流程；不繞驗證 |
| I04 | 全新 D 會員資料、共用收件人 | GET 身分成功才建對應 ATM 資料；不能臆造會員或門市 |
| I05 | 指定 COD 卻無有效門市，誠品有合法共用 ATM | 首次送單前走 ATM 備援；UI/TXT 寫實際付款，不假稱 COD 完成 |
| I06 | 共用地址缺欄位、身分不符或 API 被擋 | 備援不能掩蓋錯誤；不送 |
| I07 | 別帳號／別門市的成功範本、ATM 單冒充 COD | 不解鎖；官方核對必須正確帳號、付款與門市 |
| I08 | 門市回傳網址、ID、地址或名稱不符 | 不使用假設門市；正式 API 選項 ID 不能硬猜 |

證據：identity 分組、`funbox-api-pickup`。新帳號「有範本」與「當前 API 可送單」分開判斷。

### 04 單品／合單與 API 結帳

| 題號 | 注入情況 | 合格答案 |
| --- | --- | --- |
| C01 | 新購買工作開始，車裡已有他款 | 01 API 清車並核對，之後才 02 核對任務／03 加車 |
| C02 | 清車 DELETE 逾時／未確認空車 | 不加車、不送單。恢復未知已送單例外：先查單，不先清其車 |
| C03 | 單品混入第二款，或合單數量／品項不符 | 不送；不能只核對第一款 |
| C04 | A 合單五款，某款售罄／限購 | 允許缺款則排除該款並核對整車；不允許缺款則不送 |
| C05 | 加車期限、款數或含運上限超過 | 不無限湊滿；未知金額亦不送，不能靠送單後才發現超額 |
| C06 | 自動帶入紅利 150／250／非零 | 任何付款路線都歸零，送單 payload 與結果都需核對 |
| C07 | 使用 ATM／COD；付款配送選項已改變 | 依當次官方合法選項；不混用宅配與超商欄位 |
| C08 | checkout 回 200 但沒有單號，或明細商品／數量不符 | 不能宣布成功；保留待核對 |
| C09 | 官方成立，但 ATM 明細暫時拿不到 | 保留已成立單號，標記付款資訊待補，不再次建單 |
| C10 | 已有正式單號，本地記帳／保存故障 | 保留單號、整車與額度，不當成未送單再買 |

證據：checkout、dispatch、recovery 分組。正式 adapter/runner 搭配假 API 的測試比純函式模型更接近實際程式，但仍沒有真實建單。

### 05 壅塞、逾時、查單與重啟

| 題號 | 注入情況 | 合格答案 |
| --- | --- | --- |
| F01 | 加車已成功、回應遺失／5xx | 先查車，不盲目再加一次 |
| F02 | FUNBOX 409、即時庫存零／正數／查不到 | 分辨售罄與衝突；相同庫存指紋不反覆撞 |
| F03 | 官方明確 422 忙碌拒單 | 同車序列最多 3 次，受交易窗口限制；記錄單任務及整事件次數 |
| F04 | 模糊422、5xx、送單斷線、200不明、queued/job ID | 不同時發 N 次 checkout；保留待查，不猜官方排隊協議 |
| F05 | 429 限流、第二第三張遇忙碌 | 冷卻該帳號；新鮮觀測才派；其他帳號不停止 |
| F06 | 官方已建單、GET 暫時空列表／逾時 | 空結果不是未成立；不重送、不清車、不換付款 |
| F07 | 查單有同商品不同數量、兩個候選單、錯帳號／時間 | 不解除未知保護；合單必須唯一整車匹配 |
| F08 | 查到正確單，寫入已購與帳本後 | 才解除保護，續下一個合資格工作 |
| F09 | 程序在送單意圖保存後中斷 | 重啟唯讀對帳，不自動重播 POST |
| F10 | 通知失敗／例外／長等待 | 不影響已成立結果；通知不阻塞後續購買 |

證據：recovery、checkout、dispatch。誠品背景不明單補查上限與5分鐘窗口、FUNBOX既有立即對帳分開驗證，不假称兩站完全同一套。

## 4. 歷史重播與交叉測驗

歷史來源：FUNBOX 09/04 八款多來源訊號（四購買候選，現存證據確認成功0）；誠品10/08十五個已辨識觀測（十一候選，B確認1單）。精確放貨／售罄時間未知，仍是 null。

新模型固定用三帳號共用庫存，不複製三份。FUNBOX 新模型库存為一般款3、強化組9；誠品採歷史快照但不稱可保留庫存。商品每件100、每單運費120，競品稀少款3秒用完、其他款每10秒扣1，120秒售罄、300秒禁止新送單，**全部都是人造壓力參數**。A誠品已購UX-03是假資料，不是歷史事實。

矩陣：2平台 × 3情況 × 3模式＝18組。

| 情況 | 測什麼 |
| --- | --- |
| 順暢 | 切單品／合單／A合單B/C單品，查看假單數、件數與運費取捨 |
| 慢10秒 | 我方偵測延後，但競品和售罄時鐘不延後；少量庫存不能依舊讓ABC全買到 |
| 壅塞 | 各步驟拉長，檢查先後、共享庫存、截止、帳號隔離，不宣稱是實測延遲 |

再用50種固定亂數種子 × 兩平台 × 單品/合單，共200次交叉不變量檢查；這是一个參數化測試，不灌成200個独立案例。

測驗也測自己：故意破壞紅利、重複單號、庫存及同帳號串行，驗證器必须報錯。這是有限負向校驗，不是假稱完整 mutation testing。

模型只調用正式規則、派單與帳本模組；結帳時序是合成演算，**不是正式協調器／平台 runner 的完整替代品**。HTTP422、token401、門市與真實格式等由隔離 adapter/runner 回歸負責；模型沒假裝完成這些。

## 5. 實際瀏覽器關卡的考法

使用隔離 state、假 API 及臨時端口的控制台，不在正式頁面做破壞／取消／清車測試。

1. A設合單、B單品，儲存、刷新、重啟隔離服務。核對 DOM、設定 API 回應、派單實際設定三者一致；沒有密碼出現在 status。
2. 新增D與AA，只設定假帳密。刷新仍存在；新帳號不繼承A模式／門市；切平台名單不互相蓋掉。
3. 注入單品、五款合單、失敗、待查、ATM資料缺漏、已取消各一列。每列顯示正確結果／品項／數量／實際付款方式。
4. 展開80步、下載單筆TXT；再以帳號與結果篩選匯出。核對下載檔行數、UTF-8、台灣時間、加秒、佇列與單號；不得含假SECRET字串。
5. 注入「已成立但官方取消／仍待付款」，按更新狀態。結果必須取消，已購不刪；連點不製造重複GET，忙碌時不查。
6. 擷取這些畫面及 console；console error、儲存不落盤或下載少步，任何一個都失敗。**本輪沒有自動執行這六項實際瀏覽器操作**。

## 6. 官網與真實訂單關卡

唯讀：逐帳號 GET 官方會員身分、合法配送付款與既有訂單明細。記錄遮罩身分、時間、狀態與安全格式；不要印token／地址／完整銀行帳號。不加車、不選店、不登入恢复、不送單。失效帳號標需處理，不硬湊全通過。

若另授權實單，先確認：平台、指定帳號、品項、件數、含運上限、最多單數、付款、門市及收件人。建議分階段，不一次把所有組合都真實下單：

1. 兩平台各一次ATM單品；確認單號、唯一品項、紅利0、金額、轉帳資料／期限。
2. 有真實門市證據的帳號各一次COD；核對測試門市、配送付款及應付金額。
3. 兩平台各一次兩款合單；核對兩款數量、單一單號、運費與付款證據。
4. 所有正式訂單都保存，不自動匯款、付款或取消；取消亦須單獨授權。未授權路線維持未驗收。

不要向官網灌流量來製造壅塞或測重複POST。壅塞故障在隔離假API注入；下次自然補貨才收集實際現象。

## 7. 真實補貨成績單

每次分平台／帳號記錄：來源取得時間、派單時間、等待佇列、清車／加車／核對／送單前資料各耗時、第一次checkout起點、明確拒單次數、結果不明次數、官方成立時間、首次查單確認、付款資訊取得、已購保存、通知時間。

至少分開四個數字：候選數、合資格工作數、確認成立訂單數、確認買到件數。再列明確拒絕、略過、待確認；合單不能拿訂單數當買到品項數。

速度看偵測落差、送單前耗時、官方處理、確認延遲的p50/p95；同時核對API請求数、運費／訂單與運費／件。不訂死六秒，不拿模型毫秒宣稱真實改善；樣本少不強算p95或成功率。

硬性不合格：錯帳號、錯款／數量、使用紅利、超額、串車、無證據報成功、未知送單重送、漏掉已成立單、秘密外流。這些任何一項發生，都不能以其他多張成功抵銷。
