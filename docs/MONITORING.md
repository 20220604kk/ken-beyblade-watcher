# 平台監控邏輯

本文件說明目前程式實作，不是各網站的官方 API 文件，也不承諾補貨時的發現速度。網站自身使用的端點不等於對外提供穩定服務的開發者 API。發佈範例預設關閉監控，啟用來源與頻率須由使用者設定。

## 共通架構

```text
來源排程 → 讀取／解析 → 正規化商品與規格 → 與本機基線比對
                                             ├─ 商品通知
                                             └─ FUNBOX／誠品購買候選 → 派單總管
```

- 基線：保存商品身分、可購狀態、庫存／規格及最近觀測，後續比對新品或恢復販售。
- 第一次讀取：通常先建立安靜基線；是否通知既有商品依平台及設定而異，不把全部歷史商品當成剛補貨。
- 來源失敗：驗證頁、逾時與解析異常不等於售罄；有保留基線、來源冷卻或失敗重排機制，細節依來源實作。
- 通知與交易分流：通知用來告知觀測；購買還必須通過名單、帳號、配送與額度核對。
- 名單分工：FUNBOX／誠品購買黑名單主要禁止派單，不等於停止監控；日本商品排除關鍵字則也會影響日本來源的監控／通知。
- 頻率不是延遲保證：排程間隔、來源快取、頁數、輪替批次、網路耗時與限流，都影響實際重新觀測時間。

## 1. FUNBOX

程式：[funbox.js](../src/funbox.js)，排程與派單連接在 [index.js](../src/index.js)。

### 資料來源

| 來源 | 用途 | 目前來源快取間隔 |
| --- | --- | --- |
| 分類商品 JSON | 取得陀螺分類清單、規格與庫存 | 9 秒 |
| 集合頁商品 JSON | 補足另一入口的商品觀測 | 9 秒 |
| 搜尋 JSON 快線 | 以新品排序探索最近商品 | 3 秒 |

三路請求可並行；新鮮候選可在來源完成時先交給購買端，不必等所有來源收齊。需要時再補讀商品資料，取得可用的 variant、庫存與數量限制。

這些是來源快取的最短重新請求間隔，不是服務固定每 3 秒全部掃完。外層排程由 `funbox.intervalSeconds`、活動時段與新品熱點設定控制；外層每 30 秒執行時，3 秒快取不會自行產生每 3 秒請求。

### 判斷方式

1. 以 `/products/<slug>` 正規化商品身分，避免 API 的不同數字欄位將同款拆成多件。
2. 合併來源時考慮觀測新鮮度，不直接選最高庫存。
3. 比對新品、恢復可購與庫存；未知庫存不硬轉為 0，預購可購也不能只看現貨數量判定。
4. 庫存增加可以通知；庫存下降跨過 100／50／20／10／0 門檻才推播，不對每一件售出洗版。是否啟用庫存變動通知另有設定。
5. 非首輪發現有庫存新品後，可暫時啟動熱點追蹤；商品售罄或熱點到期後恢復一般排程。
6. 購買候選保留 product／variant／stock／qtyCap，交給派單端再次判斷，不以通知是否送達作為交易成功條件。

### 邊界

搜尋快線目前只讀設定的近期結果；不是全站無限頁掃描。快取或網站索引可能讓來源互有時間差。加車、限購及付款仍須由交易階段確認。

## 2. 誠品線上

程式：[shopping-sites.js](../src/shopping-sites.js)。誠品在程式內屬於購物網站監控器的一種來源，本文件為了說清楚而獨立列出。

### 分工

| 路徑 | 責任 |
| --- | --- |
| Holmes 搜尋 API | 關鍵字、分類、品牌與最新商品探索；讀取商品結果及對應分頁 |
| 策展探索／策展商品來源 | 尋找相關入口，補足搜尋索引尚未出現的商品；探索工作不阻塞所有其他來源 |
| 商品 `purchase_status` API | 核對候選商品的可購按鈕／庫存狀態；已可信的來源可購訊號可直接形成候選 |

保存有效查詢模板與已知商品基線；不每輪把所有歷史商品逐一重查。部分候選需要有限並行的商品狀態核對，避免探索請求堆滿。

### 排程與事件

- 搜尋型來源的外層探索間隔目前取一般設定與 3 秒的較小值；各路來源仍有自己的快取／冷卻，並非每款每 3 秒重新查庫存。
- 發現新品、補貨或規格／庫存變動可啟動該專區的熱點；其他專區維持各自排程。
- 策展入口出現只是情報，不等於每款已開賣。未來開賣時間可以產生提醒，後續仍須核對可購狀態。
- 新鮮候選可即時送至派單端，不必等整輪通知與全部探索完成。

### 失敗處理

主入口目前傳入 `esliteApiOnly: true`。API 失敗時保留已有觀測，記錄路徑健康狀態，不自動改用瀏覽器掃頁掩蓋失敗。搜尋與策展有分別的冷卻；例如搜尋 429 不代表所有其他來源都要一起停。

讀取失敗、商品不可購、帳號排隊是不同問題；監控 API 正常不代表結帳帳號可用。端點或回應結構變更仍需維護。

## 3. 其他購物網站

程式：[shopping-sites.js](../src/shopping-sites.js)。只支援已實作的來源／版型，不是貼任意網址都能正確判斷庫存。

| 來源類型 | 主要方法 |
| --- | --- |
| momo 一般商品／分類 | HTML 清單解析，加讀商品頁與可用的規格／庫存資料 |
| momo 店+指定賣場 | 賣場 API／已知商品直接核對與較低頻探索；和一般官方分類分開處理 |
| 森森／童無忌集合頁 | Cyberbiz 商品／規格 JSON 資料 |
| MM 小舖分類 | 專用商品與規格資料解析，是否啟用依設定 |
| 其他已支援清單／商品頁 | 使用對應 HTML 解析及商品補讀 |

每個專區獨立保存基線、掃描時間與錯誤；比對新品、可購恢復、庫存／規格變化，必要時加速已知商品核對。momo 一般官方分類與店+賣場分開，避免混入其他商家而誤標成官方原價商品。

部分解析限制了清單／補讀數量，清單消失也可能只是分頁或排序變動。商品價錢、可購文字與實際庫存依網站資料品質而異；監控支援不等於支援該網站的自動下單。

## 4. 日拍／日本商店

程式：[japan-auctions.js](../src/japan-auctions.js)，愛電王橋接另見 [edion-browser-bridge.js](../src/edion-browser-bridge.js)。

「日拍」是介面的日本商品來源分類，包含樂天、樂天 Books、1999、Taiyo、愛電王等已支援日本商店；不是自動出價或競標系統。

1. 樂天搜尋、樂天 Books、Taiyo 優先以 HTTP 讀取並解析；讀不到有效內容時使用瀏覽器備援。其他來源依專用網頁解析處理。
2. 愛電王若設定 Chrome bridge，就由擴充功能回傳觀測，不再對同一目標執行伺服器瀏覽器掃描。
3. 依商品名稱／型號保留 BEYBLADE X，排除舊世代及設定的日本商品黑名單。
4. 首次建立基線不通知；之後通知「新商品且可購」或「原本不可購、現在可購」。一般完整清單連續兩輪缺項才標記不可購，橋接缺項則不直接套用此判斷。
5. 依正規化型號跨來源抑制 24 小時內同款重複通知；BX-00 因為多款共用型號，另外保留名稱區別。
6. 通知可附日圓與台幣估算；目前預設換算係數為固定估值，不是即時匯率。

驗證頁、空清單與特定來源不完整結果會拒絕覆蓋基線。驗證／愛電王連續失敗會降速；需要人工驗證時不宣稱已繞過。日本來源的可購訊號也可提示已設定的日亞商品任務重新核對，但不等於已下單。

## 5. 日亞（Amazon.co.jp）

程式：[amazon-jp-monitor.js](../src/amazon-jp-monitor.js)。不是一個全站庫存 API：使用瀏覽器讀取 Amazon 搜尋、品牌頁與商品頁，另以 HTTP 更新 TAKARA TOMY 官方定價表。

### 資料與核對

- 定價表提供型號與日圓定價，依快取時間更新；讀到明顯不完整的表時拒絕取代既有資料。
- 官方賣家條件搜尋與品牌頁用來發現 ASIN，已知 ASIN 保留在資料庫，不因未出現在搜尋第一頁就刪除。
- 使用者追蹤商品與已知品牌商品按小批次輪替核對；不是每輪打開全部商品頁。
- 新品、恢復可購或價格變更的候選會核對商品頁：購買按鈕、Amazon.co.jp 賣家身分與價格條件。
- 價格不高於對應定價加設定容差、商品可購，才符合原價監控。已知且價格不變的可購商品可沿用搜尋觀測，並非每輪重新驗證賣家。
- 尚未進官方定價表的手動商品可使用使用者提供的定價；此時是人工價格基準，不冒稱已由官方表驗證。
- X／其他日本來源訊號可用作追蹤提示；收到提示本身不能取代賣家與價格核對。

首次及探索版本升級建立安靜基線；後續通知新品可購或原本不合格／不可購商品恢復合格。擋住第三方溢價，不把每次刷新相同商品當補貨。

### 排程與失敗

目前主入口設定一般節奏約 20 秒，開啟自適應時依成功／失敗調整：健康時逐步回到較快節奏，失敗時線性降速，最高 60 秒。這是外層掃描節奏，不是全部 ASIN 都在 20 秒內查完；實際覆蓋受輪替批次、頁面載入與商品數量影響。

流量限制、驗證頁或空白載入殼會報錯並保留舊資料。日本配送地區會影響可購與價格，程式會設定日本地區；無法讀取不能視為售罄。

## 與自動下單的邊界

本專案的雙平台 API 派單與結帳主功能是 FUNBOX／誠品，見 [自動下單說明](AUTO_PURCHASE.md)。其他購物來源主要提供觀測／通知；日亞另保留獨立的商品頁訂購任務模組，並非套用這兩個平台的 API 結帳契約。
