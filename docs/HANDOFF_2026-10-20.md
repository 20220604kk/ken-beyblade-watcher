### 請求合併與帳號邊界

`AmazonReadScheduler` 只合併同一工作階段、相同 key、正在進行中的讀取，完成後不快取報價。不同帳號永不合併，不共用 Cookie、購買表單或送單前報價；結帳與送單不進此佇列。

一般背景輪查會檢查單品任務：仍啟用、非互動登入、沒有錯誤／未決交易、最近 8 秒內取得 HTTP 200 且有商品標題，才略過該 ASIN 的重複背景讀取。單品停止、失敗或觀測過期後恢復輪查。這種分擔不把單品的帳號結果當作一般監控已驗證可購；搜尋發現的新候選仍由一般監控自行核對。

背景工作最多 1 項，下一次搜尋前 2 秒暫不啟動背景請求。佇列優先級是搜尋、商品確認／單品、背景。已發出的慢請求不強制取消；同時啟用更多單品任務時仍可能排隊，排程頻率不是硬性延遲保證。

### HTTP 與冷卻的處理

- 背景商品 HTTP 只使用一般監控的既有日本配送工作階段，零自動重送、零自動跳轉；不使用其他帳號的 profile。
- 必須取得商品標題與可解析的購買／日圓價格，或明確的缺貨區塊。只回標題、載入殼或缺關鍵資料不當作售罄，不覆蓋基線。
- 只有 HTTP 200 的資料不完整會將該 URL 記為需要瀏覽器呈現，下一輪再用瀏覽器，記憶體標記有效 30 分鐘。當輪不追加另一條讀取。
- 429／503、Retry-After、驗證頁與其他 HTTP 拒絕不觸發這項切換。404 僅是該商品不存在，不能誤報整站限流。
- 一般搜尋與背景共用 `general-monitor` 冷卻；各單品 profile 維持獨立冷卻。這不代表 Amazon 的風控一定按 profile 隔離，同一出口仍可能互相影響。
- 原有背景查單、商品、結帳、購物車驗證範圍仍分開，未知送單鎖不得自動清除。

### 併發資料一致性

search 與 background 使用獨立分頁、各自防重疊。商品觀測逐筆寫入共用登錄，不再用整輪舊快照覆蓋另一條工作的新資料；訊號依提交當下的前一狀態判斷，避免重播。新 ASIN 先記為 `pending_confirmation`，確認前不交付購買訊號。待確認記錄與請求診斷都有數量上限。
