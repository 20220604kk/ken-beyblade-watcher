# 誠品過期登入憑證恢復

## 已確認原因

2026-10-15 16:34 檢查：A 的保存 token 在 15:49 到期、B／D 14:30 到期、C 14:11 到期。E 已取得新 token，會員 API 與下單待命正常。

A 的官方登入回覆忙碌；B／C 被官方驗證／攔截；D 留有已關閉的登入視窗參考。這是登入恢復失敗，不是今天先前歷史失敗訂單的新證據。

## 本次修改

- 只有瀏覽器 token 不存在、已到期或會員 API 明確 401 才清理登入狀態；有效 token、逾時、忙碌及驗證阻擋不會觸發清理。
- 只清誠品 auth token／refresh token／策略／期限的 Cookie 與 localStorage，不清全站 Cookie、Cloudflare／reCAPTCHA 資料、購物車、結帳範本或訂單保護。
- 清理後正常載入官方登入頁，每次恢復最多提交一次登入表單。忙碌沿用有界冷卻；遇官方驗證即停，不以清理反覆規避。
- 已保存 session 保留，直到新登入通過會員 API 與帳號核對才覆寫；不是刪除帳號設定重新建立。
- 從外部瀏覽器匯入只在分頁內執行一次，不反覆把舊 token 寫回官網新登入後的頁面。
- 空白登入分頁不抹除保存 token 的到期顯示；已關閉分頁／context 不再殘留「登入視窗開啟」狀態。

這些修改能修正本機恢復流程，不能保證誠品解除官方驗證或忙碌，也不能延長官網簽發 token 的有效期。

## 2026-10-17：清理前移至首次登入導航之前

原流程在首次載入登入頁後才清理，若該次導航被攔截，清理便無法執行。新版在既有會員核對未能取得有效登入後、首次登入導航前：

- 只刪除同作用域中可由 JWT 證明已過期的登入 Cookie 與其登入伴隨欄位；缺少或無法判讀的值不是過期證據。
- 任一已知官網 Cookie／儲存 Token 仍有效時，保留它，不以舊保存檔強制清除新憑證。
- 此次登入分頁的初始化腳本先檢查官網當下 localStorage；只有確定過期才移除登入鍵，每個分頁只做一次。購物、安全驗證與其他網站資料不動；新登入後不重複清理。
- 到期前的有效登入續期探測不使用這項清理。
- 診斷記錄 Cookie 實際移除數、localStorage 清理是否已執行及實際移除數。若無法確認執行，不把它寫成已完成。
- 原私人 session 檔在新登入及同帳號會員 API 核對成功前仍保留，不把清理當成登入成功。

已用完全離線、隔離的 Chrome 合成頁驗證：第一個網站腳本啟動前舊登入已清除，安全 Cookie／購物儲存仍在；較新有效憑證保留。官方攔截仍會停止本次流程，不重送、不解圖、不更換 IP 或指紋。
