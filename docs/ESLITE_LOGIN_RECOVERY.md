# 誠品登入：普通 Chrome 同步與有限恢復

## 這次修復的問題

普通 Chrome 已登入 B，不代表軟體的專用 Chrome／私人 session 檔已更新。兩者相互隔離；舊 session 過期時會員 API 回 401，但普通 Chrome 可以已取得另一份有效憑證。

新增本機同步入口 `/auto-purchase/eslite/browser-session`，讓已由使用者正常登入的同帳號憑證接回 API。只接受本機控制台 Origin、明確同步標記與既有帳號欄位；不開放第三方網頁傳入，不回傳 Token。

流程：

1. 只接受誠品第一方 auth Cookie／localStorage，丟棄其他網站與追蹤資料。
2. 核對原 JWT 到期時間，不修改期限、不自行產生 Token，不接受即將過期或較舊資料。
3. GET 會員 API 與 member_detail，核對與控制台指定帳號一致；只有成功才保存。
4. 關閉軟體自身舊登入監看視窗，避免它再以舊資料覆寫新檔；不關閉普通 Chrome。
5. 原子更新本帳號 session，失敗不覆寫其他帳號；清除舊 API context 與錯誤旗標。
6. 以唯讀 API 準備會員與配送資料。同步本身不清車、不加車、不送單。

此入口可供受信任的本機診斷工具使用。新增可選 `extensions/eslite-session-sync` 背景連接器，必須另行安裝與配對；程式存在不代表已安裝／啟用。

連接器只有誠品 Cookie、storage、alarms 權限；沒有 scripting、購物操作、密碼讀取或驗證操作。Cookie 更新時及每分鐘背景檢查；相同憑證不重複呼叫會員 API。失敗至少冷卻 60 秒；伺服器同帳號核對與訂單鎖仍有效。配對碼只在本機建立，伺服器保存其雜湊；不把額外網站 Token 存入擴充 storage。每個普通 Chrome 設定檔選擇自己的帳號代號，切換帳號必須調整代號。

**實測官方登出會撤銷舊憑證**：2026-10-14 從 B 切 C、從 C 切 E 後，B、C 會員 API 均回 401，即使 JWT 到期日尚未到。不能靠複製 Cookie 宣稱多帳號長期有效。不同帳號應分開瀏覽器設定檔，不能共用前端再透過官方登出切換；有倒數也不代表 API 必然有效。

控制台新增實際 Token 倒數與到期時間；每秒本地計算，不增加官方請求。完整帳號與姓名由本機同來源專用接口顯示，普通狀態 API 仍遮罩，密碼／Token 不攤在表格。

## 自動恢復規則

- 憑證有效時沿用；不是每次都重新送帳密。一般會員心跳 10 分鐘。
- 已啟用背景登入的帳號，到期前 10 分鐘可作一次官方前端更新探測；同一到期基準不反覆探測，心跳最低 60 秒。
- 到期前探測只使用正常官方前端，不強迫登出或提交帳密。官方沒有給較新 Token，就明確記錄「未延長」，保留仍有效的舊 API 登入。
- 401／憑證到期後才使用本地帳密作一般官方登入恢復。每次只送一次，遵守既有 15 分鐘冷卻；明確忙碌則 60／120／240／480／900 秒退避。
- 實際驗證／攔截時停止自動登入，等待使用者處理。保留成功登入的資料，不更換 IP、不破解驗證、不捏造 API refresh 路線。
- 正常會員讀取不把同一憑證的到期前驗證阻擋抹掉，避免到期後又自動撞驗證。
- 匯入成功時間保存在私人 metadata 檔，重啟後仍可辨識；恢復時只在該帳號工作階段載入已驗證的 auth 資料。
- 人工驗證暫停、冷卻與探測基準會保存到本機，服務重開不重新撞登入；較新的正常登入憑證不繼承舊憑證的阻擋。

## 限制

已存帳密不能保證官方接受登入，也不能讓 Token 永久有效。API 健康、普通 Chrome 登入、專用視窗驗證、訂單成立是不同證據，不互相替代。這次不測試購買，不以登入修復宣告下單成功。

主要檔案：`src/eslite-browser-session.js`、`src/auto-purchase.js`、`test/eslite-browser-session.test.js`。
