## 3. 各平台目前如何工作

### FUNBOX

- 搜尋快線、分類與集合 API 合併；商品 URL slug 作為身份，避免同品項因來源 ID 不同而重複。
- 目前程式來源最短間隔：搜尋 3 秒，分類／集合各 9 秒。主排程可設定 2 秒，但不代表每條來源每 2 秒都發請求。
- APP 兌換商品另存排除資訊，不派單。首次建立基線與真正新品／補貨分開。
- 出現可購訊號可早期派送，不等待最慢來源；通知與購買任務分流。
- 黑名單優先排除購買；只有命中白名單才進入優先級／帳號規則。是否仍通知以平台排除規則區分，APP 排除不等同一般黑名單。
- 同帳號佇列序列化、不同帳號有限並行；支援單品／合單。一般商品 ×1、隨機強化組預設 ×3，最終仍受庫存、帳號與配置限制。
- 每日限購午夜重置是使用者採用的假設，不是已證實官方契約；誠品的既購限制另算。

### 誠品

- 策展發現優先，結合搜尋、品牌條件及既有商品基線掃描；不能因其中一條 API 回 200 就認定整波補貨完整。
- 名單流程與 FUNBOX 一致：黑名單排除購買 → 白名單資格 → 心願優先 → 帳號既購／配送資格。
- 帳號登入、API 狀態、專用瀏覽器、一般 Chrome 登入同步各有自己的狀態。可能遇到登入排隊、系統忙碌、驗證與 token 到期。
- 保留已購／未知訂單保護，不能用清 Cookie 來重置購買額度。
- 日常付款以有效的宅配 ATM／7-11 取貨付款資料為主；缺門市資料可檢查共用 ATM 備援。
- LINE Pay 是預期最終備援，但正式契約／實單支援邊界須看當前 readiness 與驗收證據，不得僅憑測試 payload 就宣稱可用。

### 其他購物網站與日本網站

- 台灣來源適配集中在 `shopping-sites.js`；墊腳石有獨立 API 模組。蝦皮／愛電王需連接器與本機配對。
- 日本來源包含既有拍賣／商店、樂天集合及單品、OCN、Nojima、日本玩具反斗城等；實際啟用清單由本機設定決定。
- 愛電王等網站可能需要官方人工驗證；程式不繞過驗證。

### 日亞：一般監控與 A/B/C 下單是兩件事

- 一般日亞監控負責商品／原價／賣家與補貨訊號；A/B/C 各追蹤一個商品，各有獨立 profile，不互相等待一般搜尋完成。
- A/B/C fast lane 以商品頁 API 讀取本輪官方 Buy Now 表單，符合全新自營／日圓原價條件後直接結帳；不在購買熱路徑先查購物車與舊訂單。
- 正式送單仍核對 ASIN、單品／數量 1、賣家、配送、日圓總額、運費及不折點。成功需要正式訂單號，不接受 purchaseId 冒充。
- LOG 只有三種步驟類別：01 商品頁面、02 安全結帳、03 取得訂單；每類可以有多筆真實事件。
- 進 02 保留入口／回應／失敗證據；普通刷新 LOG 在記憶體且可清空，訂單紀錄另外保留。
- 背景查單／待機購物車登入失敗只暫停該輔助查詢，商品監控不因此被判整體登出；真正商品／結帳登入或人工驗證仍需處理。
- 已確認未最終送單的直購錯誤才可 2 秒／5 秒／30 秒有限退避重試；最終送單結果不明維持鎖，不重買。
- 2026-10-19 CX-20 13 次失敗：6 庫存不足、6 空白結帳頁、1 結帳登入。新增精確空白頁辨識，下一輪同 ASIN 暫用背景瀏覽器 Buy Now 入口，2 分鐘後回 API；最終核價、持久化交易與單次送單仍沿用主線。
- 插件雙路是選配功能，現有個人 Chrome 插件已由使用者移除；不要因原始碼存在就擅自重裝。獨立分享版插件屬另一專案，不在這次主程式交接範圍。

### 清車與失敗處理

- FUNBOX／誠品提供手動一鍵全清；使用者已要求從正常購買流程移除固定清車步驟，勿因舊文件寫「第一步清車」又加回去。
- 日亞待機清車是不可購時滿 500 次檢查才執行的維護，不放在可購商品熱路徑。
- 加車逾時先查車，不盲加；明確售罄／限購不反覆撞；最終送單未知先查正式訂單，不把未知當失敗重送。
- FUNBOX 的付款狀態與官方生命週期分開；手動取消後應以「訂單取消」為準，不能只看待付款。

## 4. 乾淨安裝與啟動

建議 Windows 10／11 x64、Google Chrome、Node.js 24.15.0；`package.json` 最低要求 Node 20。Windows 桌面小程式另用 .NET Framework C# 編譯器與 WebView2。

```powershell
git clone --branch main https://github.com/20220604kk/ken-beyblade-watcher.git
cd ken-beyblade-watcher
npm ci
npx playwright install chromium
Copy-Item -LiteralPath .env.example -Destination .env
Copy-Item -LiteralPath config.example.json -Destination config.json
npm run check
npm run test:offline
```

上述兩個 Copy-Item 僅用於全新目錄；已有設定時先檢查，不覆寫。Google Chrome 需要另外安裝，因不少模組固定 `channel: 'chrome'`。

範例的監控與自動下單開關都是 false；各 target 的 enabled 不等於平台總開關已開。先以不帶任何私人設定的狀態確認可啟動。

日常入口：四個根目錄批次檔；或 `npm start` 前景開發。監控守護與前景開發不可同時啟動在同一資料目錄／port。

控制台：`http://127.0.0.1:3210/`。狀態：`GET /api/status`。根網址才是網頁，不要把未知 API 路徑當桌面嵌入頁。關閉頁面或小程式視窗都不等於停止監控。

桌面控制器建置：

```powershell
.\scripts\build-monitor-control.ps1 -InstallDesktopShortcut
```

此命令會下載固定版本 WebView2 SDK，產出 `artifacts/` 下 exe，並安裝桌面／啟動捷徑；應在使用者確認公司可建立開機入口後執行。桌面 exe 不是完整可攜版，不能單獨搬走。

## 5. 設定、私人資料與安全搬機

| 路徑 | 內容與搬機原則 |
|---|---|
| `.env` | 公開／私人 Discord Webhook、Bot／LINE／選配商品表；絕不入 Git |
| `config.json` | 啟用、時段、來源、優先名單、目標等；複製前先在副本關閉所有自動下單 |
| `data/state.json`／`state.json.last-good` | 基線、帳本、限購、未決交易與平台狀態；未知歷史不能當空白 |
| `data/private-purchase/.credential-key`＋`credentials.enc.json` | AES-256-GCM 金鑰與密文；密文不是可公開資料。若用安全離線方式轉移，兩者要成對保留，不貼聊天／GitHub |
| `data/auto-purchase/` | 專用 profile、平台 session、結帳與配對資料；敏感，跨 Windows profile／電腦不保證可用，優先在公司重新官方登入 |
| `data/records/amazon-product-orders/` | 日亞訂單 JSON 與 02 evidence；含私人資料，另行安全備份 |
| `records/` | 舊永久訂單資料，需另核對格式與用途 |
| `logs/`、`artifacts/` | 日誌與建置／驗證產物，不當成設定或歷史帳本 |

GitHub **不含上述私人檔案**。第一輪可以完全不搬私密資料，先驗證程式與監控；要延續既購／限購判定時，需使用者另行安全轉移並核對帳本。不要先清空再啟用。

搬移需要一致快照：先確認來源端沒有進行中／未知交易，在指定維護空檔停止來源服務，再備份資料、校驗、轉移；不要對正在寫入的 `state.json`／Chrome profile 做雙向同步。密鑰與密文外的 Chrome Cookie 可能綁 OS／帳號，不能承諾直接複製即可登入。

本機控制台有帳密檢視等高權限操作，僅綁 loopback。不要直接改成 `0.0.0.0`／路由器轉發。公司／家中遠端操作另設私有安全通道與存取控制。

## 6. 公司主跑、家中備援：建議分階段

| 階段 | 執行內容 | 通過標準 |
|---|---|---|
| A：公司開發驗收 | clone、安裝、離線測試；不帶真實帳號、不下單 | 版本固定、測試通過、私人檔未追蹤 |
| B：公司唯讀監控 | 使用者選少量來源開監控，先不發正式通知／不下單 | 實測解析、排程、基線、斷線恢復及 CPU／RAM 24 小時觀察 |
| C：指定帳號交接 | 來源停單與未決核對 → 安全轉移／重登 → 公司接手指定帳號 | 同一帳號只有一台交易主機，通知不重複、帳本一致 |
| D：家中輕量控制 | 家裡停掉已移交的重型 worker，保留控制／手動備援 | 遊戲時家裡不再跑相同完整工作量 |
| E：之後再做 | 心跳、共享事件去重、節點所有權／租約、斷網防雙主、自動接管 | 另立驗收，不靠「看不到主機」就直接重送訂單 |

公司主機斷線不能證明最後一張訂單失敗。接管前若有最終送單未知，先查官方訂單；沒有可靠證據就保留該帳號待核對，其他帳號／監控可以繼續。

目前沒有 E 階段的跨機交易鎖。第一版用使用者指定的人工切換，或分配不同帳號到不同主機，不能用複製同一份 state 當同步機制。

公司需允許電腦持續開機、連網及儲存私人購物帳號；關閉休眠／排程重啟需依公司規則。程式活著 24/7 與每個平台全天監控不同，監控時段仍由各平台設定控制。

## 7. 測試、診斷與資源

```powershell
npm run check
npm run test:offline
npm run test:commerce
npm run check:amazon-race
npm run check:edion
npm run audit:distribution
```

回歸測試有隔離 headless Chrome、合成商品／訂單及本機 API mock；不需要正式帳號。部分會建立臨時資料夾／本機隨機 port，需允許本機測試網路；它們不證明下一次補貨可成交。

`GET /api/status` 的 `performance.scope` 為 `node-only`；Node CPU／RAM 不是整機及全部 Chrome 占用。資源優化要量 Chrome 子程序、並行 browser 數、來源時段與輪詢；不要只縮 LOG 就宣稱已解決熱當。

日誌政策：例行零捕獲掃描不落盤，事件 30 天、錯誤／系統 14 天；訂單／交易／帳本／evidence 不套一般日誌刪除規則。`maintain-logs.mjs` 的刪除／套用參數需先看原始碼與 dry-run，不能遞迴刪整個 data。
