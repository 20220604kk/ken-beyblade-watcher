# 誠品第一拍基線補查

策展頁仍為主要發現來源，搜尋線同步尋找新品。第一個已確認可購的新品／缺貨轉可購商品立即交接派單，然後在背景補查本監控目標的歷史基線及手動商品資料庫。首次建立基線不觸發，單純讀到缺貨／待確認也不觸發。

## 補查規則

- 讀取現行誠品購買規則，依黑白名單篩選、優先關鍵字排序；各帳號限購、已購及結果不明的訂單仍由原派單器處理，不因補查繞過。
- 僅以正式數字商品 ID 呼叫 `purchase_status` API。平時不永久輪詢所有歷史商品，補查不啟動瀏覽器、不加車、不送單。
- 第一款先交接，不等待補查。背景最多佔用 2 個驗證槽，所有商品驗證合計最多 4 個；尚未開始的驗證依「策展 → 搜尋 → 基線」排序，不取消已在途的請求。
- 同一監控目標正在補查時合併訊號；兩輪啟動間隔至少 60 秒。每輪 30 秒後不再開始其他商品請求，已送出的請求仍受既有 4 秒 API 逾時限制，可能稍後才結束。
- 同一商品已有驗證工作時共用 Promise；本輪已得到官方可信新觀測的商品略過。補查結果不再觸發另一輪補查。
- 確認可買就交給既有觀測／派單流程。原本缺貨轉可購才增加補貨候選，穩定現貨更新新鮮度而不假報新補貨。比較的是保存基線，不能證明官方把它列在同一波。
- API 逾時、拒絕、404 或格式變更維持未知、保留基線，不偽造零庫存。未查完的品項不代表缺貨。
- 關閉監控／停止服務後不再開始後續補查，在途回應不再派單。主掃描不能以合併的舊資料覆蓋背景的新觀測。

## 紀錄與驗證

狀態存於 `commerce.shoppingSites.targets[目標ID].esliteBaselineSweep`：首款、開始／完成時間、總數、確認數、新增可購數、目前可購數、未知數、略過數，以及 completed／time_limit／stopped／error。
控制台的 `/api/status` 在對應 `shoppingSites.targets` 內提供同名欄位，方便核對最近一次補查結果；尚未觸發時為 null。

日誌僅摘要開始／結束與個別可購狀態變更，不輸出請求頭或憑證。

離線驗證：`node --test test/eslite-baseline-sweep.test.js`。測試使用假 API／可控等待，包含派單先行、限流、名單排序、訊號去重、逾時保留、時間上限、主掃描競態、停止及來源交會；不建立真實訂單。
