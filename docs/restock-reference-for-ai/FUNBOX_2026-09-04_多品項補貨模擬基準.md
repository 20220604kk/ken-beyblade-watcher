用途：提供朋友的 AI 在本機重播監控、過濾、派單、結帳與故障恢復。這是一場真實歷史事件的脫敏整理，不是即時庫存，也不是可直接送往官網的訂單範本。

## 1. 為什麼挑這一場

09/04 16:40～16:49，同一場補貨可辨識 8 個不同品項。其中 5 款在 16:41:17 同秒取得有貨訊號，之後另一個資料來源再回傳相同商品。現存證據包含分類／集合 API、掃描逾時、登入預熱失敗、HTTP 409、購物車混入兩款、指定付款未套用，以及數分鐘後才結束的工作。

適合測試的核心不是「看見商品就算買到」，而是：多來源去重、各帳號獨立佇列、過期任務淘汰、異常不拖垮其他帳號、送單前核對及成功證據。

證據標籤：

- **實測**：當日文字日誌或保存的購買記錄。
- **未知**：歷史沒有保存，必須留空，不得由 AI 猜補成實測。
- **模擬**：為可重播測試自行設定，不是當日官網數值。

## 6. 新流程測試設計（全部為模擬，不是歷史結果）

### 固定測試設定

- ABC 三帳號，各自獨立登入／購物車；A 模擬 7-11 貨到付款，B／C 模擬宅配 ATM。資料使用假身分及假付款資訊，不載入真實帳密。
- 白名單 F05～F08；F01～F04 僅通知。每款 1 件、每款一張訂單。
- 優先關鍵字設定「BX-50」：ABC 的第一個可購任務都應是 F06。其他款各帳號用不同固定亂數種子排序，測試須能重播。
- 額外已購排除案例：設定 A 已買過 F07，只排除 A，不影響 B／C；這是測試資料，不是當日已購史。
- 每單首先 API 清車並確認空車，核對任務後加車；車內唯一品項／數量須吻合。全部紅利歸零，再確認官方模擬回應允許指定配送／付款。
- 已送出而不明的訂單不得再清車、切付款或重送；只讀查單。其他帳號繼續。
- 為測試任務過期，可設定候選 TTL 120 秒及整場截止 16:46:17；兩者是合成壓力條件，不能稱為當日售罄時間。到期後只允許查詢已送出的結果。

### 測試 A：歷史故障重播

依第 3／4 節重播資料源逾時、重複商品及各帳號錯誤；無成功證據的工作不得算成功。應得到 0 張「已確認成立」，每個失敗有明確停止／待補資料／下一筆狀態。新流程會提早淘汰舊任務，因此不要求重現舊版卡住 8 分鐘。

### 測試 B：順暢、慢十秒、壅塞的對照

使用以下**人為合成**延遲，不能拿測試結果當官網實際成功率：

| 操作 | 順暢（ms） | 壅塞（ms） |
|---|---:|---:|
| 清車＋確認 | 400 | 1800 |
| 加入商品 | 300 | 1500 |
| 核對車 | 300 | 2500 |
| 結帳資料／紅利／付款核對合計 | 600 | 3000 |
| checkout 回覆 | 800 | 4500 |
| 正式單號及付款資料確認 | 400 | 1000 |

順暢：F05～F08 模擬庫存各 20、資格皆有效、無其他買家；理想上限是 3 帳號 × 4 款＝12 張。這是測試上限，歷史實績不是 12 張。

慢十秒：同一個模擬伺服器的庫存時鐘不變，將買方收到候選延後 10000ms；另外合成競品每 5 秒取走 F06 1 件，直到 0。不得只把所有時間（包括售罄）一起平移，否則沒有真的測到監控落後。

壅塞：加入歷史類型的 GET 逾時及 409。另做兩個獨立分支：409 後即時 stock=0，以及 409 後即時 stock>0。前者停止同庫存簽章重試，後者視為庫存配置衝突、有界處理，不能永久當售罄。額外注入一筆 checkout 回覆遺失但伺服器已建單，應以查單確認且 POST 只有一次。

### 模擬驗收清單

1. F01～F04 加車／送單次数皆為 0。
2. 來源重複批次不新增同帳號同商品任務；數字 ID 和路徑 slug 要映射到同一商品。
3. 同帳號 checkout 最大並行數 1；不同帳號可並行。
4. 清車未確認、車內混款、付款未套用、紅利不為 0：checkout 次數 0。
5. checkout 不明不重送；查單找不到不等於確定未成立。
6. 來源逾時不抹掉基線，通知限流不阻擋派單。
7. 故障只影響該工作或該帳號；其他帳號可繼續。已過期的待送工作不再執行。
8. TXT 每步一行：`步驟｜HH:mm:ss｜+秒｜動作｜狀態｜下一步`。
9. 輸出 ABC 各自順序、成立單、未知單、失敗／略過原因與每支模擬 API 呼叫次數；所有假單號前綴 `SIM-F-`。
