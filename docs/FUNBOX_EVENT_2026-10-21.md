# 10/21 FUNBOX 活動準備

使用者本次授權：今日搜尋快線每秒掃描；普通錯誤完成後等待 2 秒再試；09:30、09:50 各一則 DC 提醒（四個商品連結）；10:00 起四個 APP 商品各一次上架 DC，之後庫存變動不推；C 的已啟用特別任務改成 **10:00:05（台灣時間）**。不以本文件授權額外送單。

## 實作與排程

- `src/funbox-event-day.js` 僅在台灣日期 2026-10-21 有效，次日自動恢復原速度，不覆蓋平日設定。主掃描排程 1 秒；搜尋取消第二層完成時間快取，以免實際變成隔輪才讀。分類／集合備援仍沿用 9 秒快取。掃描不重疊，慢回應會使實際間隔延長。
- 普通來源錯誤後等待 2 秒；HTTP 429／503 至少 60 秒並遵守更長 Retry-After。整個 FUNBOX 公開監控共享該次冷卻，不以其他資料源繞過。
- 09:30 及 09:50 在該分鐘內各一則公開 Discord，包含海怪 `bbpr07733`、雄鹿 `bbpr07736`、黃蜂 `bbpr07730`、龍神票券 `bbpr07739` 的完整品名及商品連結。暫停系統／停止官網監控時不發送。
- 10:00 後只有新鮮官網掃描發現的指定 APP 商品才觸發上架通知；特別任務直接讀到產品 JSON 時也可觸發同一去重入口。每商品一次，不加入一般採購候選，也不發其庫存變動。
- 通知標記保存在主狀態 `commerce.funboxEventDay20261021.notifications`，先持久寫入發送意圖，成功記為 sent，回應不明記為 unknown，不重啟重送。這是避免重複的機制，不能保證網路失敗時 DC 必達；可從狀態及日誌核對。
- `reschedule` 是同源 CSRF 保護的特別任務操作，只改未執行任務的時間，保留啟用狀態、加密序號及順序；有執行／未決／已成單紀錄時拒絕。
- 時間欄改為秒精度，10:00:05 不會因開啟或儲存介面而被截成 10:00:00。09:59:05 預熱官方登入與門市；10:00:05 才開始實際兌換流程。
- 商品未上架：至少隔 1 秒重讀；開放後前 30 秒庫存 0 先視為尚未就緒，不將四筆直接略過。後續明確售罄仍依原規則略過，庫存資料缺漏仍等待重讀。
- 使用者最後指定不因一般失敗停等人工，本次透過 `reschedule` 啟用 `continuousRetry`：序號暫未生效、逾時、資料未更新以 1／2／4／8 秒退避自動重試，不自動清車或略過有效待確認序號；明確庫存 0 才略過。移除本次的 30 分鐘強制結束。已確認屬於本筆、尚未送單的車可接續流程，不重加已存在的商品。
- 生日券實測確認 HTTP 200 並不保證重算已反映在第一個 HTML。故套券後以同一個已確認車 URL 重讀，等待指定券、正折抵及紅利 0；不反覆繞回 `/cart` 多車入口。正式送單回應不明時保持啟用並自動查官方新單；保留送單意圖，不盲重送同一單，確認後才繼續下一組。

## 最終檢查修正

實際官網多車頁也包含 `#checkout-v3`，而且 React 商品列用 `id: <variant>_normal_<collection>`，不一定有 `variant_id`。原特別任務可能錯把它當正式結帳頁，或找不到目標車。已修正路徑判斷及複合 ID 核對，仍要求唯一指定單品 ×1 才選車，錯車不猜。真實 A 頁面只唯讀查證，沒有擅自刪除既有品。

生日券驗證與正式帳號現況留在本機 `artifacts/handoff/`，序號、會員、車 token 不寫入本文件。生日券測試不等於 APP 券成功折價；APP 商品的正式券、總額 555 及 COD 成單仍須當下官方資料通過。
