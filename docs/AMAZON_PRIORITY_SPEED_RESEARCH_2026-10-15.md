## 2. 實際架構與延遲來源

### 已經做對、不必重做的部分

- A／B／C 自動下單已各自有 API 排程、持久工作階段及任務內鎖；A 不會直接被一般搜尋的 running 鎖擋住。
- A 已使用 2 秒目標週期、唯讀前置檢查並行，合格後沿用本輪新取得的官網表單，不是重新開商品頁再點擊。
- 結帳中不重刷、POST 不盲目重送、結果不明先查單、原車非空不擅自清除，應全部保留。

### A. 一般直查被綁在探索後面

`src/amazon-jp-monitor.js:scan()` 先更新到期型錄與品牌資料、讀一般搜尋，再選普通直查商品。普通直查每輪只選 2 件，加 1 件背景已知商品；目前優先池是 7 件。

所以單品資料庫不是每款每 15–20 秒查一次。搜尋讀取失敗時，普通直查可能完全沒執行。定價前專線例外，但目前沒有啟用項目。

### B. 購買訊號等完整輪次結束

現有程式把候選與直查結果全部收集成 `eligible` 後，才呼叫 `onAvailabilitySignal`。先查到的商品必須等剩下商品核對完成。

通知迴圈雖然對單一商品不 await 購買訊號，但會 await 該商品 Discord 傳送；因此第一款推播慢，第二款的購買訊號也會晚。

離線重播使用真正的現有 `AmazonJapanMonitor.scan()`，每次商品核對及推播各設定 1 秒虛擬成本：三款分別於 1／2／3 秒核對完成，購買訊號卻在 3／4／5 秒才交付。這證明相依關係，**不是實際網站節省 2 秒的測量**。

### C. 定價未知被當作不進入一般直查的理由

CX-20／BX-54 已在手動庫，但沒有型錄定價或人工定價，普通直查會在讀商品頁之前跳過。A 另有 CX-20 API 輪詢，不代表普通資料庫也在查。

本輪以現有解析器重新讀官方型錄：HTTP 200、150 件，仍沒有 CX-20／BX-54；所以不能假稱只要刷新型錄就一定補得出價格。

合理的拆分是：可以先讀取／通知「自營報價出現、定價待確認」，但價格基準未完成前禁止自動購買。不自行猜定價，不用同系列商品的價格代替。

### D. 指標會高估真正直查量

`lastDirectCheckedCount` 目前計算選入直查的數量，而非真正完成商品頁核對數量。離線重播三件選入、其中一件無定價時，畫面計數 3，實際商品核對僅 2。

應拆成：排入、實際請求、成功、失敗、跳過，另記每款最後成功讀取時間與資料年齡。

### E. 沒有跨層級資源優先權

排程彼此獨立，不等於實際網路、CPU 解析與共用狀態寫入具有優先權。暫未量到 CPU／磁碟為主瓶頸，不把它們說成已證實根因；目前最明確的是串行網頁讀取與訊號延後。

2026-10-15 日亞記錄讀到 2,046 行成功摘要與 10 行掃描失敗；不是獨立請求數或成功率。最近失敗由程式歸類受限，無法據此推出 Amazon 真正的限流門檻。

## 3. 建議架構：遵守使用者的三層順序

```text
優先權總管（排程獨立、共用流量預算）
├─ P0 自動下單：實際結帳／送單／結果核對，最高優先
│  └─ 下單目標報價：先維持約 2 秒目標；符合立即交接
├─ P1 單品直查：獨立 API 報價輪替，不依賴一般搜尋
└─ P2 日亞探索：搜尋／品牌頁／其他已知商品，使用剩餘預算
```

「自動下單」內仍須讓實際交易優先於平時報價輪詢。進入交易時，不再發起低優先讀取；已發出的唯讀請求可結束，但不得取消或重播交易請求。

### 速度安排（提案，不是已套用的保證）

| 層級 | 起始目標 | 執行原則 |
| --- | --- | --- |
| 自動下單目標 | 約 2 秒報價；合格立即結帳 | 先保留 A 的已測節奏；其他帳號逐一驗證，不一口氣拉滿 |
| 手動單品庫 | 小名單每款約 5–10 秒作為研究目標 | 先驗證 API，再依總預算調整；是每款年齡，不是整池計時器 |
| 一般搜尋 | 約 30–60 秒起 | 用來找未知 ASIN，不承擔已知目標搶購的第一線 |
| 品牌／型錄資料 | 獨立較慢排程 | 到期更新也不能阻擋單品與下單；缺定價單獨顯示 |

目前 A 約 30 次／分鐘、C 約 12 次／分鐘報價。如果 5 款手動商品各每 10 秒再查一次，就再加約 30 次／分鐘；若各每 5 秒查，則加約 60 次。這還沒算搜尋、重導、交易與其他網站資源。因此不能把每層都設成 1 秒，或宣稱固定請求量一定安全。

同工作階段、ASIN、賣家條件與配送範圍一致的監控讀取才考慮合併。不同帳號的可購條件不能直接視為相同；A 的 fresh 送單表單、CSRF、Cookie 不得拿給 B／C 使用。

## 4. 最有價值的實作順序

1. **最先拆掉等待關係。** 每款完成必要核對就先交購買訊號，Discord 改獨立佇列；保留首輪安靜基線、補貨去重與帳號鎖。
2. **拆出單品直查排程。** 搜尋錯誤不能卡住單品；每款有獨立資料年齡、下次檢查及失敗冷卻，選名單時先跳過不可執行項目。
3. **驗證監控工作階段的 AOD HTTP 讀取。** 沿用正常工作階段，不重繪完整商品頁。A 已實測可用不等於匿名監控工作階段也一定可用，必須另驗證。無法確認的報價保持未知，不冒充售罄。
4. **加總預算與交易優先權。** 結帳時暫緩低優先請求，無饑餓時再補低優先工作；使用有限並行，不把全部商品同時打出去。
5. **只在穩定證據足夠後縮短下單輪詢。** 本次單次報價 P95 已約 1.2 秒，不直接改成 0.5 秒。若研究 1.5 秒，必須同步量實際間隔、資料正確性、阻擋與長尾，而不是只改設定文字。
6. **最後研究 API 立即購買。** 目前缺完整安全實測，保留現有已走通的加車結帳路線作主線。需要另外授權才進行加車／真實送單測試。

輪詢一般日誌可合併寫入，但加車／送單意圖與未知交易的耐久保護不能改成未落盤就送單。下單效能必須分別量：補貨發現、合格判斷、發起送單、正式單號確認。

## 5. 下一階段驗收

- 模擬搜尋逾時、型錄更新、Discord 逾時：單品與下單不能跟著停住。
- 同時出現五款補貨：每款核對完立即派訊號，後續訊號不等待前一款推播。
- 下單工作入場後：低優先新請求停止搶資源，既有交易不被取消。
- 同 ASIN 多來源命中：合併監控訊號，但帳號分開重新核對與防重送。
- 429／503／Retry-After：服從官方冷卻，不用換帳號、IP 或前端逃避阻擋。
- 缺定價仍可偵測報價，但不得自行把價格設定成核准購買上限。
- 小名單逐項統計最新有效資料年齡與 P50／P95；型錄／搜尋失敗不清空庫存基線。
- 真實下單只有在另行確認商品、帳號、件數與金額上限後測量。本輪沒有新實單。
